
# F024: Family chat and notifications

- **Status:** Proposed
- **Branch:** Not created
- **Pull request:** Not created

## Goal

Let accepted members of the same F018 family exchange private messages and notice new activity inside the Family tab.

## User flow

1. A member opens **Family → Chat**, chooses another accepted member, and sends a message.
2. The recipient sees an unread indicator, opens the conversation, and replies.
3. Each member can adjust in-app notification preferences.

## In scope

- One-to-one conversations with persisted, paginated message history.
- Unread counts, in-app new-message notifications, and a Family-tab notification center.
- Read receipts and typing indicators, subject to the decisions below.
- Membership and participant access checks on every request; pending, NON_USER, removed, and unrelated people cannot read or send.
- Empty, loading, send failure, and disconnected states.

## Out of scope

- Anonymous chat and PIN protection (F027), group chat, attachments, email/push alerts, and cross-family conversations.
- Another invitation or role system; F018 remains authoritative.
- Social-feed comments and reactions (F023).

## Wireframe or UI changes

Add **Chat** and **Notifications** views under Family: accepted-recipient list, conversations with unread counts, message thread, composer, and notification settings. Do not list pending or accountless people as recipients.

## API changes (proposal)

- `GET /api/family/{familyId}/conversations`: caller's conversations and unread counts.
- `POST /api/family/{familyId}/conversations`: start or reuse a conversation with an accepted member.
- `GET /api/family/{familyId}/conversations/{conversationId}/messages?before={cursor}`: paginated history.
- `POST /api/family/{familyId}/conversations/{conversationId}/messages`: send validated text.
- `POST /api/family/{familyId}/conversations/{conversationId}/read`: update caller's read position.
- `GET` / `PATCH /api/family/notifications`: caller's notifications and preferences.
- Return `401` without a session, `404` for inaccessible data, and `403` for a disallowed write.

## MongoDB changes (proposal)

Store conversations with family ID and participant User IDs; messages with conversation ID, sender ID, text, and time; read positions per participant; notification records and preferences per recipient. Index messages by conversation and time. Retention and deletion need approval.

## Architecture decisions

- Use F018 accepted membership; family ADMIN access does not expose other people's conversations.
- Keep message content out of notification previews until the privacy choice below is decided.
- Check both participant identity and current family membership on every message read and send.

## Acceptance criteria

- Two accepted members can exchange messages and see the same ordered thread after reload.
- A third family member cannot open their conversation.
- The recipient's unread count increases for a new message and clears after reading.
- A removed member loses conversation access immediately.
- Notification preferences affect alerts without hiding message history.

## Local verification

Test access with two participants, a third accepted member, a pending invite, and a removed member. Check unread counts across two browser sessions and reloads.

## Open questions

1. Is periodic refresh sufficient initially, or is live delivery required for the first release?
2. May READONLY family members send messages?
3. What happens to message history when a member leaves or deletes an account?
4. Are read receipts and typing indicators enabled by default, optional, or deferred?
5. Should notifications show message text, sender only, or an unread count only?
