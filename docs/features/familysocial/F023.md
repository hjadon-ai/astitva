# F023: Family Social feed

- **Status:** Done
- **Branch:** `feature/F023-family-social-feed`
- **Pull request:** Not created

## Goal

Give accepted members of an F018 family a private place to share updates, photos, and milestones. Posts belong to an existing family; F018 continues to own membership and invitations.

## User flow

1. An accepted member opens **Family → Social** and sees posts for the selected family.
2. They write a post, optionally attach a photo or mark a milestone, and choose a family-wide or selected-member audience.
3. Allowed members read and respond. The author can edit or remove their post.

## In scope

- Chronological feed with text, optional photos, milestones, and announcements.
- Family-wide or selected-member visibility within one F018 family.
- Reactions, comments, and one pinned announcement subject to moderation rules.
- Recheck accepted membership and audience on every request. Pending and NON_USER people cannot read posts.
- Empty, loading, upload failure, and removed-post states.

## Out of scope

- Separate family groups, invite codes, join requests, or duplicate roles.
- Public profiles, cross-family discovery, outside sharing, and direct messages (F024).
- Real-time notifications (F024).

## Wireframe or UI changes

Add a **Social** view under Family with a family selector when needed, a composer, and a feed. Each post shows author, time, audience, content, reactions, comments, and viewer-permitted actions.

## API changes (proposal)

- `GET /api/family/{familyId}/posts?before={cursor}&limit={n}`: paginated posts visible to the caller.
- `POST /api/family/{familyId}/posts`: validated text, type, audience, and optional photo reference.
- `PATCH` / `DELETE /api/family/{familyId}/posts/{postId}`: author edit/delete; moderator access needs approval.
- `POST` / `DELETE /api/family/{familyId}/posts/{postId}/reactions`: caller's reaction.
- `GET` / `POST /api/family/{familyId}/posts/{postId}/comments`: visible comments.
- Return `401` without a session, `404` for an inaccessible family or post, and `403` for disallowed writes.

## MongoDB changes (proposal)

Posts need family and author IDs, type, text, optional photo reference, audience, timestamps, and deletion state. Reactions and comments need post and author IDs. Index the family feed by creation time. Photo storage, limits, and cleanup need approval.

## Architecture decisions

- Use F018 accepted membership and roles rather than another family/group model.
- Resolve selected-member visibility against current accepted membership on every read.
- Keep the initial feed chronological.

## Acceptance criteria

- Accepted members see a family-wide post; pending, removed, and unrelated accounts cannot.
- A selected-member post appears only to its author and selected accepted members.
- A person cannot react to or comment on a post they cannot read.
- Removing a post hides its content from normal feed reads.
- Selecting one family never reveals another family's posts.

## Implementation decisions

Owner-delegated small implementation: text max 2000, comments max 500 UTF-16 code units; at most 100 selected accepted user IDs; pages default 20/max 50. Photos are JPEG/PNG up to 2 MiB with signature validation, stored in the post document in the current environment database. Only authenticated audience-authorized image responses serve photos; no public upload URL, new storage service or environment configuration. Photos are removed with deleted posts; failed uploads create no orphan. No automatic retention expiry. Original image metadata is retained; no metadata-stripping claim. Any accepted viewer of a post may remove it or pin/unpin an announcement; only the author edits. One pinned pointer belongs to the family. Selected audiences use stable account IDs so membership re-entry restores access after current membership checks.

## Implemented API and verification

Implemented endpoints follow the post/comment/reaction paths above. Photo creation uses POST posts with multipart `payload` (JSON post fields) and optional `photo`; JPEG/PNG bytes belong to that post. GET posts/{postId}/photo checks current membership and audience and serves no-store image bytes. PUT posts/{postId}/pin accepts `{pinned: boolean}`; one announcement pin is represented by the family pointer. Author PATCH supplies full text/type/audience/recipientIds plus positive integer `version`; stale edits return 409. Photo bytes remain attached on text edits. Likes are idempotent and capped at 1000 distinct accounts.
